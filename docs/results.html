Fluent Bit v5 vs OpenTelemetry Collector

Progressive signal benchmark — logs → +metrics → +traces → +tail-sampling. Each tier adds one telemetry signal, so each row's delta is the incremental cost of that signal. Every arm ran a 2 h rampup validity gate → 24 h+ soak, one engine live at a time, exporting real signals to Dynatrace under otel-demo + hipster-shop load on an Istio 1.29 cluster.

Engines under test: OpenTelemetry Collector-contrib v0.159.0 · Fluent Bit v5.1.1. Pins frozen at setup.

Headline

Fluent Bit is the lighter engine at every tier — ~5× lighter memory on logs, ~11× on the metrics arm, ~41% lighter memory / ~44% lighter CPU at the full signal set — with zero loss throughout. The Collector is the capability engine: native gRPC trace ingress and per-datapoint metrics. No memory leak in either engine at any tier (all runs tail-flat, ≤1.81% drift).

✅ Tier 4 erratum corrected — E8 re-run complete (2026-09-24): an earlier version claimed tail sampling is Collector-only. That is incorrect — Fluent Bit v5's sampling processor (type: tail) supports tail sampling. Tier 4 has been re-run as a like-for-like comparison with both engines on identical Design-A policy. Corrected numbers are reflected below. Tiers 1–3 are unaffected.

Incremental cost of each added signal

  • Logs (T1): both cheap & leak-free over 24–26 h. Fluent Bit ~30% lower CPU, ~5× lower memory, ~30% lower cost/1M at matched ~755 rec/s.
  • +metrics (T1→T2): a high-cardinality istiod-CP + Kepler scrape on a dedicated metrics StatefulSet. Widest gap of the ladder — Collector ~78 MiB vs Fluent Bit ~7 MiB / 2 m → ~11× memory advantage for Fluent Bit. Neither leaks under the Kepler stressor.
  • +traces (T2→T3): OTLP trace path on a dedicated traces workload. Fluent Bit holds its lead — ~200 vs ~337 MiB, ~100 vs ~180 m — with zero dropped vs the Collector's small non-zero loss. Trace ingress differs by design (FB HTTP :4318 only vs Collector gRPC :4317).
  • +tail-sampling (T3→T4, E8 like-for-like): the most expensive single add — and the widest cross-engine gap of the benchmark. With identical Design-A policy on both engines (keep-errors OR keep-slow≥250ms, 100k-trace buffer), the collector traces pod runs at 131 MiB while Fluent Bit's at 28 MiB — a ~4.7× sampler-memory advantage for Fluent Bit. Total 5-pod: 391 vs 69 MiB (~5.7×) at 2h. Both zero-loss, both tail-flat.

Both engines keep identical Design-A policy (100k-trace buffer, decision_wait=10s). Fluent Bit's sampling processor is ~4.7× more memory-efficient than the collector's tail_sampling processor at the same settings.

Reproduce this benchmark: engine pins, pipeline configs (both engines × 4 tiers), the load harness, and the step-by-step run guide (2 h rampup → 24 h soak) are in this repository. An importable Dynatrace dashboard (dashboards/fluentbit-vs-collector-benchmark.dashboard.json, cluster-parameterized) reproduces these views live against your own Grail data.

Methodology: serial single-engine — deploy one engine → validate signal received + census 0-restart + load reaching the app → rampup gate → soak → tear down → next engine.
